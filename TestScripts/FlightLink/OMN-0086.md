# OMN-0086 — Android reliable commands on impaired links

## Scope and production paths

The Android app uses **Microsoft Java SignalR** over HTTP negotiate, WebSockets, and SignalR Long Polling fallback; it does **not** use raw UDP for application commands. Rust OmniHub's `/signalrhub` handles both transports with the same authenticated invocation interpreter. Tailscale/direct or DERP relay selection is underneath this HTTP transport; a flight network that blocks both VPN access and every reachable HTTPS endpoint cannot be solved by retrying a TCP socket.

The previous client incorrectly guessed the home Hub's IPv4 address by changing the last octet of **any** 10/8 or 192.168/16 Wi-Fi address to `.37`. OMN-0085 observed it replacing a configured endpoint with unreachable emulator `10.0.2.37`. This implementation **never guesses or writes the Hub URL during reconnect**. A configured Tailscale, HTTPS proxy or custom host stays authoritative; the legacy explicit LAN `*.37` configuration still permits configured public-IP fallback. The last *successful* URL wins among still-configured candidates. The Android default-network callback wakes reconnect on network transitions; existing backoff retains jitter, the connection-start allowance rises to 25 s (from 10 s), and agent/reminder/outbox synchronization starts again on authentication.

## New command protocol

On Android, discrete commands are persisted with **UUID**, method, arguments, creation time and pending/attempt/outcome in a bounded private SharedPreferences outbox *before* network transmission. A queue holds at most 48 pending commands and 12 final outcomes, with a 64 KiB payload limit. Successful/failed/unknown history records discard argument bodies; pending bodies remain device-local until delivery or expiry. Regular queued actions expire locally after 5 minutes; short-lived clicks/window actions after 40 seconds. They do not execute later merely because the phone reappears days afterward.

Android calls `RunReliableCommand(UUID, method, arguments[], createdAtMillis)` via authenticated SignalR, with a 45-second completion timeout. Rust validates method/size, rejects stale or future timestamps, then **atomically writes an admission receipt before applying a side effect**. It persists up to 2048 receipts for 2 hours, including fingerprint of method+arguments (no plaintext command body). `GetReliableCommandStatus(UUID)` yields `not_found`, `pending`, `succeeded`, or `unknown`. An existing UUID cannot be reused with different arguments. The Rust journal path is `%LOCALAPPDATA%\OmniHub\state\android-command-receipts.json`; a corrupt/unwritable journal fails closed.

If a response is lost, Android reconnects and **queries the prior UUID first**. A succeeded/unknown receipt terminates the retry, and a pending one waits; *only* a `not_found` receipt permits a retry with the **same UUID**. Bounded exponential backoff with jitter and an eight-attempt cap apply, on top of the existing connection backoff. A Hub crash after admission but before outcome persistence reports **unknown** (manual verification) and never repeats that side effect. Server-side dispatch errors are conservatively unknown, because a side effect may have been partially performed. The Remote screen displays the most recent pending/succeeded/failed/unknown result, and the Android log records the UUID prefix. **A succeeded receipt means Rust's command handler returned successfully**, not that an unrelated browser/plugin/UI consumer visibly completed its downstream task.

Covered: command/macro execution, browser commands, window activation/close, monitor cycling, shutdown-mode toggle, discrete text, clicks, mute, volume, shutdown scheduling, plus file append/create-directory calls. Continuous pointer motion, held key/down/up, drag state, interactive terminal streams, legacy agent commands and generic unclassified `send()` calls **are not replayed**: replaying them could cause stuck keys or unintended UI actions. TaskBoard edits, reminders and Jarvis already have separate reconciliation/outbox paths, and were not replaced.

## Repeatable checks and evidence

Use the OMN-0085 disposable proxy and an **updated** Rust Hub process (do not aim this new option at a still-deployed previous binary). The optional receipt test is read-only except for the bounded Hub journal: it submits `ProcessMacro("echo flight-receipt-probe")`, which **rewrites text but does not execute a macro**, then queries the receipt across a *new* SignalR connection and repeats the **same UUID**. It checks duplicate/result convergence and records elapsed milliseconds. The protocol probe is a native WebSocket client; the separate `flight-link-android.cjs` flow uses the actual Java client.

```powershell
# No production service restart or network-interface modification. Run against
# an isolated updated Rust Hub with OMNIHUB_TEST_PORT set (or after authorized
# installation of the new Hub binary).
node TestScripts/FlightLink/flight-link-run.cjs --reliable --upstream-port <port> --out E:/_AgentScratch/Tasks/Omni/OMN-0086/reliable
node TestScripts/FlightLink/flight-link-run.cjs --reliable --full --upstream-port <port> --out E:/_AgentScratch/Tasks/Omni/OMN-0086/reliable-full
# Run the updated Android APK in the disposable emulator through the proxy:
node TestScripts/FlightLink/flight-link-android.cjs --serial emulator-5554 --profile slow800 --seconds 35
```

Synthetic profile coverage remains `clean`, 300/800/2000-ms RTT, connection-reset approximation of 1/3/10% loss, `noUdp` (TCP-only), path switching, 10-s and optional 120-s outages. `--reliable` appends `reliable_initial_uncertain` and `reliable_outcome` measurements to `commands.jsonl` including request UUID, initial receipt, final Hub state, same-ID replay count, and elapsed time. An interrupted first response is **not** classified as failed or safe-to-replay without the later status query. The proxy reset/loss model is **not packet-level netem**, and `noUdp` does not prove a real Tailscale DERP or Air China path. HTTPS-only additionally requires a trusted test certificate, test hostname, and `--tls-cert/--tls-key`, as described in OMN-0085 README.

### Remaining limits

- Real device/aircraft HTTPS/Tailscale policy, DERP vs direct route and certificate trust depend on external network reachability. If all endpoints are unreachable, requests remain pending then expire/unknown.
- The desktop Hub can perform an action and die before its final receipt is durable. Exactly-once **replay prevention**, not guaranteed knowledge of completion, is possible; that state is explicitly **unknown**.
- Some legacy `send()` operations still lack per-command receipts; the implementation deliberately does not auto-replay them until they have explicitly safe semantics and a server-side journal.
- Source compilation is **not deployment**. Live production Rust Hub and the user’s phone were not restarted or replaced, to avoid disrupting concurrent Omni work. After an authorized rollout, run the disposable `--reliable` profile and the real updated APK through the flight proxy, inspect `commands.jsonl` outcomes and phone UI, and test HTTPS with trusted certificate.
